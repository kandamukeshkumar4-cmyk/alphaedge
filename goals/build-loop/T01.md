# T01 — Kalshi WebSocket stream connector

Spec: docs/project/BUILD_LOOP_BACKEND.md §3 T01.

## Design (first-principles, written before code)

What must be true here:
- The existing tick path (`price_feed_worker.run_live_tick_once`) already owns the
  contract: normalize → epsilon-persist to `odds_snapshots` → `hub.publish(slug,
  {slug,yes,no,ts,alert})`. A stream must feed THAT contract, not invent a parallel
  one, or the frontend WS hub and DB history fork.
- Constraint: Kalshi markets are stored `source="kalshi"`, `external_slug`=ticker,
  `external_id`=event_ticker, `slug`=`ks-{ticker}` (per kalshi_live_ingest). The
  stream subscribes by ticker and must map ticker→slug via the Market table.
- Constraint: single asyncio event loop, one shared AsyncSession per unit of work,
  Redis available, DomainEventBus exists. The stream is long-lived; DB writes must
  use short-lived sessions (`AsyncSessionLocal()`), never hold one open for the
  socket lifetime.
- Root-cause note: the real value of a stream over polling is *latency* and
  *orderbook deltas* (needed by T03 diff engine), not just "faster ticks". So the
  base abstraction emits a typed `StreamEvent` with kind `tick|orderbook_delta`,
  not just a price float — T03 will consume the deltas.

Derived approach:
- `streams/base.py`: `StreamEvent` dataclass + abstract `MarketStream` owning the
  reconnect/heartbeat/resubscribe state machine (jittered backoff 1s→cap, heartbeat
  watchdog, connection-state property). Subclasses implement only: build subscribe
  frames, parse a raw frame → StreamEvent(s).
- `streams/kalshi_ws.py`: concrete Kalshi v2 client. Parsing is a PURE function
  (`parse_kalshi_frame`) so tests need no socket. The socket I/O is thin and mockable.
- Wiring: a `_market_stream_loop` in main.py started under `live_feed_enabled &&
  kalshi_ws_enabled`; its callback opens a short AsyncSessionLocal, reuses the exact
  persist+publish logic. To avoid duplicating that logic, extract the
  persist-one-tick body from `run_live_tick_once` into a reusable
  `persist_and_publish_tick(db, slug, yes, source, ...)` helper and call it from both.

Guardrail check: read-only market data; no keys (public WS); no order path touched;
no execution language. PASS.

## Break findings (adversarial pass), worst first
1. [FIXED] Refactor dropped the `yes` local used by the terminal-status block in
   run_live_tick_once → F821 (would crash on any resolved/closed live market).
   Caught by ruff; recomputed yes in that block. Regression covered by existing
   live-tick tests.
2. [HOSTILE INPUT] Malformed/partial/out-of-range frames → parser returns [] and
   never raises (9-case parametrized test). Bytes frames decoded defensively.
3. [CONCURRENCY] stop() during reconnect backoff wait and mid-recv → clean stop via
   stopped-event wait_for; CancelledError propagates and stops. Tested.
4. [CARELESS OP] DB write per event uses a short-lived AsyncSessionLocal with
   rollback-on-error; no session held for socket lifetime; one bad event can't drop
   the stream (callback exception isolation tested).
5. [KNOWN LIMITATION, not a crash] ticker→slug map is resolved once at stream start;
   markets ingested mid-session are missed until the stream reconnects. Acceptable
   for T01 (acceptance is latency + degrade + reconnect). FOLLOW-UP for T03/perf:
   bound session lifetime or refresh the map on the ingest cadence. Noted here so it
   is not silently dropped.
6. [PERF] callback awaits sequentially (natural backpressure); a session-per-event
   under extreme burst is a cost — batching deferred to perf pass, noted.

## Latency note
exchange_ts→publish is a synchronous pure-parse + async hub.publish; StreamEvent
.latency_ms exposes exchange→received for the T12 latency badge. Parse path is
trivially < 50ms (no I/O between recv and callback).

## Design (first-principles)

What must be true:
- Guardrail 3: this is a FEATURE / CONTEXT signal, never a standalone trade trigger.
  It is persisted for research/UI and can feed the model as context, but does not
  place orders or (by itself) fire the analyst.
- Flag-gated OFF by default (`instability_enabled=False`) — additive, opt-in.
- Derived from the EXISTING news_signal pipeline output (volume_score, sentiment,
  sources_count) — no new data source. Pure, testable scoring.

Derived approach (all original):
- `signals/instability.py`:
  - `EVENT_CATEGORIES`: my own small taxonomy — conflict, election, economy,
    disaster, policy, health, markets, other — each with keyword patterns.
  - `categorize_event(text) -> str` — pure keyword match, default "other".
  - `instability_score(*, volume, sentiment, sources, sources_norm=20) -> float`:
    composite 0-1 = clamp01(0.6*volume + 0.4*min(sources/sources_norm,1)) *
    (0.5 + 0.5*min(|sentiment|,1)). Monotonic in volume/sources/|sentiment|; clamped.
  - `InstabilityService.compute(text, *, volume, sentiment, sources) -> (category,
    score)`; `compute_and_store(session, market_slug, ...)` persists a
    signal_events row (type="instability", headline_eligible=False) when enabled,
    else no-op.
- config: `instability_enabled` (default False).
- Tests: categorize keywords + default; score monotonicity + clamp + boundaries;
  compute returns (category, score); store persists when enabled, no-op when off.

Guardrail: feature/context only; never a standalone trigger; no order path; no LLM in
the score path. No schema change (signal_events exists). PASS.
